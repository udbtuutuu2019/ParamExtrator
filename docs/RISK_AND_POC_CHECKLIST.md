# 高风险技术假设 · 技术难点 · POC 验证清单

> **项目**：ParamExtrator（弹性数据提取 Harness 流水线）
> **依据**：`docs/TECHNICAL_DESIGN.md` v1.3（已与需求对齐）+ 需求文档
> **版本**：v1.0（2026-10-15）
> **原则**：每个 POC **只验证一个技术假设**，**不开发完整业务功能**；用小成本换取"能否走通"的确定答案。

## 一、高风险技术假设（R 系列）

> 判定标准：**若该假设不成立，会导致架构返工、核心功能不可用、合规/安全失守或生产目标不达标。**

| 编号 | 高风险假设 | 为何高风险 | 若不成立的后果 | 现有证据 |
|------|-----------|-----------|---------------|----------|
| **R1** | instructor + DeepSeek 在生产目标模型上能**稳定**产出符合 schema（含 `extra="forbid"`）的结构化结果 | 整条流水线的基石；模型名可能退役、function-calling 与严格 schema 可能冲突 | 架构层选型返工，退回手写解析 | 部分（POC 已验证枚举/doc较稳定，未验 `extra="forbid"`、未定最终模型名） |
| **R2** | **自研"针对性修复"**能在 **N=2** 内收敛（收到错误签名+原始输出后自我纠正） | 核心功能；需求硬性要求"修复循环"，设计把重试全交给自研层 | Fallback 率飙升，修复循环形同虚设 | 无（仅验过 instructor 的**通用**重试，未验自研针对性提示） |
| **R3** | **6 层注入防御**端到端有效（尤其"输出复核"能压制注入抬高 `urgency`） | 需求点名安全要求；安全失守=严重故障 | 输出被劫持，安全评级失败 | 部分（POC 单轮验证 urgency 未被抬升，未验完整 6 层链） |
| **R4** | **本地 PII 扫描**（正则/实体）对 NRIC/密码/卡号**高召回**，且卡尾号覆写正确 | 合规风险；需求要求 `detected_pii` 准确 | 漏检=合规风险；误报=噪音 | 无（扫描器未实现） |
| **R5** | **10,000+ ops/min** 吞吐可达成（受 DeepSeek 并发/限流硬约束） | 需求明确要求 README 覆盖生产就绪性；并发需求 ~334 | 生产目标不达标；需多 key/多 Provider/队列改造 | 无（容量模型为纸面估算） |
| **R6** | **所有异常路径都不崩溃**（"绝不抛未处理异常"契约） | 需求硬性要求"优雅兜底、不崩溃" | 违反核心契约，评审失败 | 无（未做故障注入） |
| **R7** | **不完整响应**（`finish_reason=length`）可被检测并归类 | 设计新增 `INCOMPLETE_RESPONSE`；instructor 是否暴露 `finish_reason` 未验 | 截断响应被误判为合法/漏判 | 无 |
| **R8** | 修复轮 `temperature=0.2~0.3` 确实**提升**收敛（vs 0） | 若成立则需分离温度配置 | 用 `temp=0` 亦可（更确定） | **POC-2 已验：无差异** → 决策 D9 统一 `temp=0` |
| **R9** | **错误签名归一化** + `attempts/repairs` 口径（仅计自研层）可实现且自洽 | 影响测试断言与日志契约 | 日志/测试断言失真 | 无 |
| **R10** | 幂等缓存 + **单飞防穿透**在高并发下正确 | 生产扩展核心 | 缓存击穿打爆 LLM | 无 |

> **R1–R6 为"高"**（架构/核心功能/安全/合规/生产目标/契约），**R7–R10 为中**（局部机制）。

## 二、技术难点（D 系列，非假设而是已知难点）

| 编号 | 难点 | 说明 |
|------|------|------|
| **D-1** | **"针对性修复提示"的收敛设计** | 提示词要携带原输出+精确错误+最小改动约束，还要避免多轮上下文膨胀——难在"改对且不越改越差" |
| **D-2** | **注入防御的"不误杀"平衡** | 多层防御要压住攻击，又不能拒绝正常对话（如正常提及"系统"一词） |
| **D-3** | **PII 高召回 vs 低误报的平衡** | 正则易误伤（订单号/日期）；卡尾号又需显式排除 |
| **D-4** | **"永不崩溃"的全面覆盖** | 需穷举所有异常出口并保证收敛，边界多 |
| **D-5** | **确定性 vs 模型非确定性** | 修复轮引入温度探索，又要保证"状态路径确定" |
| **D-6** | **10k/min 的成本/限流工程** | 缓存、退避、多 Provider、队列——工程复杂 |
| **D-7** | **错误签名的归一化映射** | 把 Pydantic/JSON/传输各类异常统一成可读、可断言、可修复的签名 |

## 三、POC 验证清单

> 每个 POC 独立、最小、可判定。**不含完整业务流程**。

### POC-1｜instructor × DeepSeek 结构化输出稳定性 【对应 R1】🔴
- **验证目标**：确认 instructor + DeepSeek 在**生产目标模型**下稳定产出符合 schema（含 `extra="forbid"` + `Literal` 枚举 + `max_length`）的结果；确认可用模型名。
- **最小验证范围**：4 个基准用例 × 3 次；schema 加 `extra="forbid"`；`max_retries=0`；分别跑 `deepseek-chat` 与 `deepseek-flash`（禁思考模式）。**不接业务逻辑。**
- **验收标准**：
  1. 首轮 schema 通过率 **≥ 95%**；
  2. `extra="forbid"` **不误伤**正常输出（0 次因多余字段误判）；
  3. 至少 1 个模型名可用，并记录 P50/P95 延迟；
  4. 产出**模型选型结论**。
- **现状**：已部分完成（见 `docs/POC_INSTRUCTOR_DEEPSEEK.md`），**需补** `extra="forbid"` 与模型名确认。

### POC-2｜自研"针对性修复"收敛性（N=2）【对应 R2 + R8】🔴
- **验证目标**：模型收到"错误签名 + 原始输出片段 + 针对性修复提示"后，能否在 **≤2 次修复**内收敛；并确认修复轮温度策略。
- **最小验证范围**：用 **mock** 在首轮注入 4 类可修复错误（枚举错 / summary 超长 / 缺字段 / 幻觉字段），跑自研 Repair 循环（N=2）；对同一输入比较 `temp=0` 与 `temp=0.25`。**不接业务。**
- **验收标准**：
  1. 可修复错误在 **≤2 次**内的收敛率 **≥ 80%**；
  2. 不可修复（连续同错）能触发**单调性熔断**，不死循环；
  3. 产出**温度策略建议**（是否采用 0.2~0.3）。

### POC-3｜6 层注入防御端到端 【对应 R3】🔴
- **验证目标**：针对 TX-003 类间接注入，最终输出合法、`urgency` 不被抬升、无 `SYSTEM COMPROMISED` 透传。
- **最小验证范围**：3~5 个注入变体（显式覆盖 / 角色劫持 / 输出操控），跑"检测 → 语义隔离 → 调用 → 输出复核"**最小链**；断言最终 `output`。**不接完整业务。**
- **验收标准**：
  1. **100%** 输出为合法 schema JSON；
  2. **0 次** `urgency` 被注入抬升为 CRITICAL；
  3. 注入被标记 `injection_suspected=true`；
  4. 字符串 `"SYSTEM COMPROMISED"` **永不**出现在合法输出中。

### POC-4｜本地 PII 扫描准确率 + 卡尾号覆写 【对应 R4】🔴
- **验证目标**：本地扫描器对关键 PII 高召回，且卡尾号覆写规则正确。
- **最小验证范围**：4 个基准用例 + 10 个正/负样本，跑 PII 扫描器；含卡尾号覆写规则。**不接 LLM。**
- **验收标准**：
  1. NRIC `S9123456A` **100%** 命中；
  2. 密码 `SuperSecretPass123` **100%** 命中；
  3. TX-001 卡尾号经覆写输出 **`false`**；
  4. 误报率 **≤ 10%**（在给定样本上）。

### POC-5｜吞吐/并发可达性（DeepSeek 限流）【对应 R5】🔴
- **验证目标**：确认目标并发下调用 DeepSeek 的成功率、延迟与**限流触发点**，判断 10k/min 可行性。
- **最小验证范围**：压测脚本，**50 / 100 / 200 并发**各发一小批（如各 100 请求）；记录 429、P50/P95 延迟、错误率。**不接业务。**
- **验收标准**：
  1. 得到"**可持续并发上限 + 首次 429 触发并发 + P95 延迟**"数据；
  2. 给出 **10k/min 是否需**多 key / 多 Provider / 队列的结论；
  3. 校准 §11.1 容量模型（原为纸面估算）。

### POC-6｜"永不崩溃"契约 + 不完整响应检测 【对应 R6 + R7】🔴
- **验证目标**：所有异常路径收敛到定义终态、不抛未处理异常；`finish_reason=length` 可检测。
- **最小验证范围**：mock 注入 超时 / 限流 / 非法 JSON / 空输入 / `max_tokens` 截断 等故障，跑 Orchestrator，断言返回对象。**不接业务。**
- **验收标准**：
  1. **100%** 返回 `SUCCESS / REPAIRED / FALLBACK` 之一；
  2. **0** 未捕获异常向上传播；
  3. `max_tokens` 截断被分类为 `INCOMPLETE_RESPONSE`。

## 四、执行顺序与优先级

| 顺序 | POC | 理由 |
|------|-----|------|
| 1 | **POC-1** | 基石；若不过，架构选型要返工，后续全免 |
| 2 | **POC-2** | 核心功能；决定修复循环是否成立 |
| 3 | **POC-3** | 安全；与 POC-2 共用最小链，可并行 |
| 4 | **POC-4** | 合规；独立、可并行（不依赖 LLM） |
| 5 | **POC-6** | 契约；依赖 POC-1/2 的骨架 |
| 6 | **POC-5** | 生产目标；成本最高，放最后（不影响本地功能） |

> **POC-1/2/3/6 共享同一套最小骨架**（schema + orchestrator 空壳 + mock client），
> 建议一次性搭好后分别验证，避免重复劳动。

## 七、POC 执行结果

### POC-1｜instructor × DeepSeek 稳定性 + extra="forbid" —— ✅ **PASS**（2026-10-15）

**执行脚本**：`poc/poc1_forbid.py` ｜ **模型**：DeepSeek 真实 API

| 检查项 | 结果 |
|--------|------|
| schema 约束自检（确定性） | **PASS** — 正常对象通过；幻觉字段被 `forbid` 拒绝；空摘要被 `min_length` 拒绝；非法枚举被拒绝 |

| `deepseek-flash`（禁思考）首轮通过率 | **12/12 (100%)** ｜ P50 1176ms ｜ P95 1540ms |

**验收对照**：
1. ✅ 首轮通过率 ≥95%（两模型均 100%）
2. ✅ `extra="forbid"` 不误伤（0 次误判，且能正确拒绝幻觉字段）
3. ✅ 两个模型名均可用
4. ✅ 模型选型结论已产出（见下）

**结论**：
- **R1 已验证通过** —— instructor × DeepSeek 稳定，`extra="forbid"` 兼容良好。
- **模型选型**：`deepseek-chat` 与 `deepseek-flash`（禁思考模式）**均可用**，延迟接近。
  - 默认选 **`deepseek-chat`**（更成熟）；`deepseek-flash` + `thinking:disabled` 作为备选。
  - **重要**：`deepseek-flash` **必须显式禁用思考模式**，否则与 function-calling 冲突（HTTP 400）。
